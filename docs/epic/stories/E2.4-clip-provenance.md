# E2.4 — Per-clip provenance in the manifest

**Epic:** E2 · Assets and pipeline · **Depends on:** E2.2 · **Size:** S
**Plan:** `docs/superpowers/plans/2026-10-08-looped-loader-oss-readiness.md` → Task 6
**Spec:** §4.3 (manifest contract), §9 (accepted risk)

## Goal

Turn the licensing boundary from a paragraph in `NOTICE` into a machine-checked field:
every clip in the published manifest declares where it came from and under what licence,
and the pipeline refuses a clip that declares neither. The 32 existing clips get the
honest value — `unverified` — rather than a comfortable one.

## Scope (checklist)

- [ ] Manifest schema: each clip gains
      `provenance: { source: string, sourceUrl?: string, license: string, author?: string, retrievedAt?: string }`.
      `license` is a free string with a documented convention (`CC0-1.0`, `CC-BY-4.0`,
      `public-domain`, `unverified`), not a closed enum — new licences appear, and an enum
      would force a schema bump for each one.
- [ ] `tools/transcode` reads a sidecar `gifs/<id>.provenance.json` when present. Without
      one it writes `{ source: "reddit", license: "unverified" }` and records a
      `license-unverified` **review** finding in `qc-report.md`, not an error: the clip is
      published deliberately, and the report must say so on every run.
- [ ] The core's `parseManifest` keeps ignoring unknown fields (so `provenance` cannot
      break a consumer on an older runtime) but validates the shape when the field is
      present: `source` and `license` must be non-empty strings if `provenance` exists.
- [ ] `packages/assets/scripts/verify.mjs` fails when any clip lacks
      `provenance.license` — this is the check that makes the field real for future
      contributions, including ones added by a stranger.
- [ ] `qc-report.md` gains a "Provenance" section listing every clip by licence value.

## Acceptance criteria

- `pnpm --filter @topclans/looped-loader-assets test` passes on the committed assets and
  **fails** when a `provenance` block is deleted from one clip — proved once by deleting
  it, observing the failure, and restoring the file.
- `qc-report.md` lists all 32 clips under `unverified`, and the count matches the manifest.
- Core manifest tests still pass with an unknown `provenance` field present, and a
  malformed `provenance` (empty `license`) is rejected as `manifest-invalid`.
- A pipeline integration test with a sidecar fixture writes the sidecar's values, and one
  without a sidecar writes `unverified` plus the review finding.

## Out of scope

- Automated licence detection or any legal assessment. This story records claims; it does
  not verify them.
- Changing which clips are published — that is E4.5 and it is owner-gated.

## Risks

- **The field can be a lie.** A contributor can write `CC0-1.0` over a stolen clip. The
  honest limit is to require a source URL so the claim is reviewable, and to say in
  `CONTRIBUTING.md` that the reviewer checks it. E4.3 owns that half.
- Marking the existing 32 as `unverified` makes the exposure explicit in a public
  artifact. That is the point: the accepted risk is already recorded in the spec, and a
  manifest that pretends otherwise would be worse than one that says so.

## Open decisions

1. Should `unverified` block a *future* release rather than merely being reported? Decided:
   it warns for the set that ships with the accepted risk, and blocks once E4.3's policy
   is in place for newly added clips. The pipeline needs a way to tell "grandfathered"
   from "new" — the `retrievedAt` date is not enough, so the assets package pins the
   grandfathered ids in `provenance-exceptions.json`, and any id not in that file must
   carry a real licence.
