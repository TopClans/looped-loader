# E5.3 — Post-release verification

**Epic:** E5 · Release · **Depends on:** E5.2 · **Size:** S
**Plan:** `docs/superpowers/plans/2026-10-08-looped-loader-oss-readiness.md` → Task 10
**Spec:** §8 (acceptance criteria 5–7)

## Goal

Verify the release from the outside, the way a consumer experiences it. Everything up to
here was verified from inside the repository, where the package resolves through workspace
links and every path is the one the author typed. A `200` from the repository is not a
release; an install from the registry is.

## Scope (checklist)

- [ ] In a scratch directory **outside** the repository: `npm install` all three published
      packages at the released version, then run the README's self-hosted recipe end to end
      — copy `clips/` out of `node_modules`, point `base-url` at it, render the component.
- [ ] `npm audit signatures` → verified attestations for all three packages.
- [ ] jsDelivr: `HEAD` a real clip URL from the published assets package, record the status,
      the content type, and the version actually served. Then remove the "unverified"
      marker from the CDN recipe in the README, in the same commit that records the result.
- [ ] npm package pages: provenance attestation present and linking to the repository and
      the workflow; `LICENSE` visible; README rendered; keywords and repository link
      present.
- [ ] GitHub: community profile 100 %, the release exists with notes, the tag is protected,
      the repository is public.
- [ ] Write `docs/verification/<date>-release.md` with every command and its actual output.
      A report that paraphrases instead of quoting is not evidence.

## Acceptance criteria

- The report exists and quotes the output of each command above.
- The scratch install resolves the published version, not a workspace link — verified by
  reading `node_modules/<pkg>/package.json` and confirming there is no `workspace:` field.
- `npm audit signatures` reports verified attestations for all three packages.
- The README carries no remaining "unverified" marker, and each recipe states the version
  it was verified against.

## Out of scope

- Testing every hosting configuration a consumer might invent. The two documented recipes
  are the contract.
- Performance measurement in the consumer's app; the measurements that exist (bundle
  budget, main-thread cost) were taken on the demo and are documented as such.

## Risks

- **jsDelivr caching.** It can serve a stale version briefly after a publish; pin the exact
  version in the URL and state the version observed, so a mismatch is visible rather than
  mysterious.
- A consumer's bundler may resolve the assets package differently from the scratch test
  (Vite vs webpack vs plain static copy). The scratch test covers the documented recipes
  only, and that limit is stated in the report.
