# E5.1 — Release automation: trusted publishing with provenance

**Epic:** E5 · Release · **Depends on:** E3.5, E4.4 · **Size:** M
**Plan:** `docs/superpowers/plans/2026-10-08-looped-loader-oss-readiness.md` → Task 9
**Spec:** §8 (acceptance 8), §10 (preconditions)

## Goal

Releases happen in CI, carry a cryptographic link to the source, and need no long-lived
token anywhere. This is both a supply-chain improvement and the removal of the last
credential from this project.

## Verified facts

Measured on 2026-10-09, when the release actually ran:

- **`npm trust` requires the package to exist.** With the owner authenticated, the POST to
  `…/-/package/@topclans%2flooped-loader-core/trust` answered `404 Not Found` while the package
  did not exist, and succeeded once a placeholder `0.0.1` had reserved the name. The
  design-time `--dry-run` probe that appeared to accept an unpublished name never reached the
  registry.
- **Writes on this account need proof of presence.** `npm deprecate` from a granular access token
  answers `EOTP`; configuring a trusted publisher opens the browser challenge at
  `https://www.npmjs.com/auth/cli/…`. The tag publish needed none of it — OIDC is the proof.
- **The release itself:** tag `v0.1.0` → run `37915146807` green → three packages published with
  a provenance attestation each, verified by `npm audit signatures`.

From npm's own documentation and the local CLI, 2026-10-08:

- **Provenance** requires a supported cloud CI/CD provider on a cloud-hosted runner
  (GitHub Actions, GitLab CI/CD, CircleCI); a public repository; a `package.json`
  `repository.url` that matches the GitHub repository **case-sensitively**; and
  `--provenance --access public`. Provenance is **not supported for private repositories,
  even when publishing public packages**.
- **Trusted publishing** (OIDC) needs npm CLI ≥ 11.5.1 and Node ≥ 22.14.0, GitHub-hosted
  runners, and a trusted-publisher configuration naming the workflow file exactly (filename
  only, `.yml`/`.yaml`). It removes the need for `NPM_TOKEN` entirely.
- With trusted publishing from a public repository, **provenance is generated
  automatically** — no `--provenance` flag needed.
- A newly created trusted-publisher configuration **must complete its first successful
  publish within 2 days, or it expires** and must be recreated.
- Local npm is **11.21.0** and ships **`npm trust`**:
  `npm trust github <package> --file <workflow> --repo <owner/repo> [--allow-publish] [--dry-run] [--json]`,
  plus `npm trust list` and `npm trust revoke`. So the configuration can be done from the
  CLI and verified programmatically, without the npmjs.com UI.
- `npm@latest` (12.2.0) refuses this machine: it requires node ≥ 22.22.2 and the local node
  is exactly 22.22.0.

## Scope (checklist)

- [ ] `.github/workflows/release.yml`: `on: push: tags: ['v*']` and
      `workflow_dispatch` with a `dry_run` input;
      `permissions: { id-token: write, contents: read }`; `runs-on: ubuntu-latest`;
      `actions/setup-node` with `node-version: 24` (npm 11) and
      `registry-url: https://registry.npmjs.org`. No `cache:` input, and **no**
      `package-manager-cache` either — the design-time text asked for
      `package-manager-cache: false`, which setup-node does not define; the dry run of
      2026-10-09 warned `Unexpected input(s) 'package-manager-cache'` and the line did
      nothing. Not caching is achieved by not asking for a cache.
- [ ] Publish step in dependency order — core → vue → assets — because a partial release
      where the second package fails is the failure this order makes recoverable.
      `pnpm -r publish --access public --no-git-checks` publishes in workspace order and
      rewrites `workspace:*`; confirm that ordering in the dry run rather than assuming it.
- [ ] The dry-run job (`workflow_dispatch` with `dry_run: true`) runs
      `npm pack --dry-run --json` per package, uploads the output as an artifact, and fails
      if any tarball is missing `LICENSE` or contains `gifs/`, `src/` or `test/`.
- [ ] **No** `NPM_TOKEN` secret anywhere, and `publishConfig.provenance` is left unset so
      OIDC decides.
- [ ] `docs/release.md`: the tag → CI → npm → GitHub Release flow, the version-bump
      procedure, the SemVer and deprecation policy, and what to do when a release is wrong
      (deprecate; never unpublish).
- [ ] Owner step, one-time, per package:
      `npm trust github @topclans/<pkg> --file release.yml --repo TopClans/looped-loader --allow-publish`,
      then `npm trust list @topclans/<pkg>` to verify. Configure it **when the release is
      imminent**, because of the 2-day window.
- [ ] After the first successful publish, restrict traditional token access for each
      package (npmjs.com → package → Settings → Publishing access → require 2FA, disallow
      tokens).

## Acceptance criteria

- The dry-run job is green from `workflow_dispatch`, and its artifact shows all three
  tarballs with the expected file lists.
- Pushing a `v*` tag publishes all three packages, and the npm package page shows a
  provenance attestation linking to the repository and the workflow.
- `npm audit signatures` in a scratch directory reports verified attestations for all three
  packages.
- `npm trust list` shows one GitHub configuration per package, and no `NPM_TOKEN` exists in
  the repository's secrets.

## Out of scope

- Staged publishing (`npm stage publish` + a maintainer's 2FA approval). It is the
  strongest posture and it is documented in `docs/release.md` as the next step if a second
  maintainer appears; with one maintainer it adds a manual step for no additional
  protection.
- GitLab or CircleCI configuration. GitHub Actions is where this project lives.

## Risks

- **The 2-day window.** Configure the trusted publisher and publish the same day, or the
  configuration expires and the error is not obviously about time.
- **`repository.url` case sensitivity.** `TopClans` vs `topclans` fails at publish time
  with `ENEEDAUTH`, which reads like an authentication problem. E4.1's manifest check
  exists specifically to catch this earlier.
- **The first publish may need a traditional path.** `npm trust github <package>` on a
  package that does not exist yet is unverified — the npm docs describe configuring a
  trusted publisher from the *package's* settings. Two orders are possible: publish `0.1.0`
  with a short-lived token and configure trusted publishing for `0.1.1`, or confirm that
  `npm trust` accepts an unpublished package name. **Verify with `npm trust … --dry-run`
  at the start of this story and record the answer here**, because it decides the shape of
  E5.2.
- A tag pushed while the workflow is broken leaves a version in the registry that cannot be
  unpublished. The dry-run job exists so that a broken workflow is discovered before a tag.
