# E4.2 — Community health files

**Epic:** E4 · Open-source readiness · **Depends on:** E4.1 · **Size:** M
**Plan:** `docs/superpowers/plans/2026-10-08-looped-loader-oss-readiness.md` → Task 2
**Spec:** §9 (risks), §11 (out of scope)

## Goal

GitHub's community profile reaches 100 %, and every file in it says something true about
*this* project. The measurable part is the health percentage; the part that matters is that
a stranger can find out how to contribute, how to report a vulnerability, and who decides.

## Scope (checklist)

- [ ] `CONTRIBUTING.md`: prerequisites (pnpm, ffmpeg), the story cycle from `RUNBOOK.md`,
      the TDD expectation, commit style, the PR checklist, how to run the transcode
      pipeline, the clip-licence requirement (links E4.3), and what a reviewer will look
      for.
- [ ] `CODE_OF_CONDUCT.md`: Contributor Covenant 2.1, with a contact route that actually
      works (GitHub's private reporting or an address the owner monitors — decide with the
      owner, do not invent one).
- [ ] `SECURITY.md`: supported versions, private reporting through GitHub Security
      Advisories, and what response to expect. State honestly that this is a
      single-maintainer project with no SLA.
- [ ] `SUPPORT.md`: where to ask (Discussions for questions, issues for defects), and what
      is explicitly out of scope so the answer is "no, by design" rather than silence.
- [ ] `GOVERNANCE.md`: who decides, how a second maintainer is added, and the bus-factor
      statement — one maintainer, and what a fork should expect if they stop.
- [ ] `CHANGELOG.md`: Keep a Changelog format, SemVer, with the `0.1.0` entry written at
      E5.2.
- [ ] `.github/ISSUE_TEMPLATE/bug_report.yml`, `feature_request.yml`, `config.yml`;
      `.github/PULL_REQUEST_TEMPLATE.md`.
- [ ] `.github/dependabot.yml`: npm and github-actions, weekly, grouped by ecosystem.

## Acceptance criteria

- `gh api repos/TopClans/looped-loader/community/profile` reports `health_percentage: 100`
  with `code_of_conduct`, `contributing`, `issue_template`, `license`,
  `pull_request_template` and `readme` all non-null. This is the acceptance test, and it is
  run rather than assumed.
- Each file contains at least one project-specific fact (the clip policy, the bundle
  budget, the QC gate, the six error codes). Boilerplate with the project name swapped in
  does not count and should not exist.
- The issue template asks for the browser, the Vue version and the asset hosting mode —
  the three things every real bug report for this component needs.

## Out of scope

- A docs site, a forum, a Discord. `SUPPORT.md` points at GitHub Discussions.
- Translation of community files. English only for `0.1.0`; a contributor may add
  translations later under their own name.

## Risks

- Files that nobody reads become stale and then misleading. Mitigation: each one is short
  enough to be read, and `PROGRESS.md` gets a debt item if any of them starts contradicting
  the code.
- `health_percentage` counts presence, not quality. It is used here as a floor, not as the
  goal.
