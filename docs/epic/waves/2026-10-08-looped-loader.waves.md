## Wave 5, part two — story E3.1 in the main session — started 2026-10-08T17:33Z — base d1b8ef9 — runner lead

- NOTE: E3.1 is the plan's only main-session story, and it earned its place twice. The first browser load showed **0 of 32** clips playing: the demo's `sync-clips.mjs` copied the `clips/` directory but never `manifest.json`, so Vite's SPA fallback answered `/clips/manifest.json` with `index.html` at status **200**, the loader's `response.ok` check passed, `response.json()` threw, and all 32 instances landed in `manifest-invalid`. A 200 that is HTML is worse than a 404, which is exactly why the case deserves a screenshot. Fixed in `c9db3ce`: copy the manifest beside the clips, point `base-url` at the directory holding both, add a data-URI icon so no favicon 404 counts as a failed request, and stop the scenario cards from printing an error code the loader never produces there.
- NOTE: with the layout fixed, 16 of 32 loaders still died — non-deterministically (12, then 16, then 16 playing across three loads), with **no** `error` event on any `<video>` element and a clean network log. Two control experiments settled it: 32 plain `<video>` elements on the same clips all reached `readyState >= 2`, so the browser was not the limit; and delaying every manifest response past `delayMs` produced **32/32 playing with exactly 32 manifest requests**, against 64 requests and half the loaders dead without the delay. The cause is in the core — `attach()` called `resolve()` immediately, bypassing `delayMs`, and `start()`'s timer then called it a second time; the second pass re-entered `selectNext()`, which marks the clip it just selected as failed, so a one-clip pool reported `no-clips` and errored. Fixed in E1.3's second fix round.
- NOTE: acceptance criterion 6 was verified the hard way — Playwright's `reducedMotion: "reduce"` media emulation, not a stubbed `window.matchMedia`: 32 spinner roots, **zero** `<video>`, `data-state: idle`, and **no** request for any clip.
